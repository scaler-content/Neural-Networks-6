Does it matter where weights start?

The question behind everything in this read.

Take two networks with identical architecture, identical data and identical everything, except for how their weights start. One begins at all zeros, the other with random values. Same training, same number of epochs. Do they end up learning the same thing?

The natural guess is that it shouldn't matter as long as training runs long enough: both will converge eventually, perhaps one more slowly. That assumption is exactly what this read breaks.

The short answer

No. A network that starts with identical weights doesn't learn slowly, it doesn't learn at all: in the lecture's run, the zero-initialized network ended at chance-level accuracy after 200 epochs. And even random weights can fail if their scale is wrong. Section 02 shows both failures, then the rest of the read covers how the optimizer moves the weights once they have a sensible start.

By the end you can

  • Explain why zero (or identical) initialization breaks a network through symmetry.
  • Connect initialization scale to vanishing and exploding activations, a different cause from the activation-driven version.
  • Choose Xavier or He initialization by activation function, and implement both with nn.init.
  • Implement and compare SGD, momentum, RMSprop and Adam with torch.optim.
  • Explain Adam's bias correction intuitively, and why learning-rate scheduling still helps Adam.
  • Spot a realistic AI-suggested initializer or optimizer mismatch using evidence.

Part 1Zero initialization

Initialize every weight to zero and train with plain full-batch SGD (learning rate 0.05, 200 epochs). Here is what happened.

1.0986 → 1.0985loss, first epoch to last. ln(3) ≈ 1.0986 is the loss of guessing uniformly among 3 classes.
33.7%train accuracy, against 33.3% chance level for three classes
Trueall rows of the first hidden layer's weights are identical
0.0max difference between any two rows of that layer

The loss barely moved. Why would starting at zero, specifically, cause that, rather than just a slow start? The answer is in the weights: every row is exactly identical, not similar, identical to the last decimal.

Why it never recovers

With all weights at zero, every neuron in a layer computes the exact same output from the same input, so every neuron gets the exact same gradient and the exact same update. Step through the loop below.

    ↻ Back to step 1, on every epoch, no matter how many run.

    Key idea: symmetry breaking

    The whole layer is stuck acting like one neuron, forever. Random initialization isn't a formality: it is what lets different neurons become different neurons.

    Code: the model factory, training loop and weight check
    def make_model(init_scheme, seed=0):
    torch.manual_seed(seed)
    model = nn.Sequential(
        nn.Linear(7, 32), nn.ReLU(),
        nn.Linear(32, 32), nn.ReLU(),
        nn.Linear(32, 32), nn.ReLU(),
        nn.Linear(32, 32), nn.ReLU(),
        nn.Linear(32, 3),
    )
    for layer in model:
        if isinstance(layer, nn.Linear):
            if init_scheme == 'zero':
                nn.init.zeros_(layer.weight)
            elif init_scheme == 'xavier':
                nn.init.xavier_uniform_(layer.weight)
            elif init_scheme == 'he':
                nn.init.kaiming_uniform_(layer.weight, nonlinearity='relu')
            nn.init.zeros_(layer.bias)
    return model.to(device)


def train_full_batch(model, epochs=200, lr=0.05):
    opt = optim.SGD(model.parameters(), lr=lr)
    crit = nn.CrossEntropyLoss()
    losses = []
    for _ in range(epochs):
        opt.zero_grad()
        loss = crit(model(Xtr), ytr)
        loss.backward()
        opt.step()
        losses.append(loss.item())
    return losses


model_zero = make_model('zero')
losses_zero = train_full_batch(model_zero)
acc_zero = (model_zero(Xtr).argmax(1) == ytr).float().mean().item()

print(f"loss: {losses_zero[0]:.4f} -> {losses_zero[-1]:.4f}")
print(f"train accuracy: {acc_zero:.1%}  (chance level for 3 classes: 33.3%)")

# Check the actual weights: is every neuron in a layer identical?
W1 = model_zero[0].weight.detach()
print("all rows of the first hidden layer identical:", torch.allclose(W1, W1[0:1].expand_as(W1)))
print("max difference between any two rows:", (W1 - W1[0:1]).abs().max().item())

    Part 2Random, but the wrong scale

    Random weights break the symmetry, but they bring a second question: how big should the random values be? The lecture's test builds a 10-layer, 100-unit-wide ReLU network, feeds in a batch of 64 random inputs, and records the standard deviation of the activations after each layer, for three weight scales.

    2.928 → 236,230.672Too large (std 0.5): layer 1 to layer 10 activation std. Explodes.
    0.058 → 0.000Too small (std 0.01): layer 1 to layer 10. Vanishes to zero.
    0.811 → 0.570He-scaled (std 0.141, from √(2/100)): stays roughly stable across all 10 layers.

    Too-large initialization multiplies the activation magnitude at every layer until it is astronomical. Too-small initialization shrinks it to zero within a few layers, which is dead signal, the same practical outcome as the zero-init case but less obvious. Try it yourself below.

    Common misconception

    “Exploding and vanishing gradients are only about activation function choice.” The version covered in Classes 1–2 was activation-driven. This is a different cause of the same symptom: even with ReLU, the wrong initialization scale alone reproduces it.

    Code: build a deep ReLU net and measure activation std
    def build_deep_relu_net(n_layers, width, init_std):
    layers = []
    for _ in range(n_layers):
        lin = nn.Linear(width, width)
        nn.init.normal_(lin.weight, mean=0.0, std=init_std)
        nn.init.zeros_(lin.bias)
        layers += [lin, nn.ReLU()]
    return nn.Sequential(*layers)

x = torch.randn(64, 100)

for label, std in [("too large", 0.5), ("too small", 0.01), ("He-scaled", (2/100)**0.5)]:
    net = build_deep_relu_net(n_layers=10, width=100, init_std=std)
    out = x
    stds = []
    for layer in net:
        out = layer(out)
        if isinstance(layer, nn.ReLU):
            stds.append(out.std().item())
    print(f"{label:12s} (std={std:.3f}): layer 1 -> layer 10 activation std = "
          f"{stds[0]:.3f} -> {stds[-1]:.3f}")
    Output
    too large    (std=0.500): layer 1 -> layer 10 activation std = 2.928 -> 236230.672

    Part 3Xavier vs. He

    Xavier (Glorot) initialization sizes the random spread to keep variance stable assuming a symmetric activation such as tanh. He (Kaiming) does the same math for ReLU specifically: ReLU zeroes out half its input range, so it needs a larger spread to compensate. Class 2 used He initialization without fully explaining why. It is built for exactly the activation function used throughout this course.

    Code: compare the two initializers
    def train_and_report(init_scheme, label):
    model = make_model(init_scheme)
    losses = train_full_batch(model, epochs=100)
    print(f"{label:10s}: loss[0]={losses[0]:.4f}  loss[-1]={losses[-1]:.4f}")
    return losses

l_xavier = train_and_report('xavier', 'Xavier')
l_he = train_and_report('he', 'He')
    Output
    Xavier    : loss[0]=1.1196  loss[-1]=0.7770

    Ask an AI assistant which initializer to use for this network. If it says Xavier without flagging the ReLU mismatch, that is worth catching.     Interview angle: “Your model trains but never beats random guessing. First three things you'd check?”

    All-identical or all-zero weights (symmetry); an initialization scale that has exploded or vanished the activations before training even starts; and a learning rate that is actively working against the first two. Not a data problem and not a bug in the loss function, those are further down the checklist.

    03

    Momentum, properly named

    A running average of gradients, now one keyword argument.

    Class 2 built momentum by hand with a manual velocity update. In PyTorch it is momentum=0.9. The finding from Class 2 still holds: plain SGD takes the same size step regardless of how consistent the recent gradients have been. Momentum keeps a running average of gradients, a velocity, so a direction that has stayed downhill for a while builds speed, and noisy back-and-forth directions cancel out.

    Code: mini-batch training, plain SGD vs momentum
    def make_dataloader_batches(batch_size=128):
    n = len(Xtr)
    perm = torch.randperm(n)
    return [(Xtr[perm[i:i+batch_size]], ytr[perm[i:i+batch_size]]) for i in range(0, n, batch_size)]


def train_mini_batch(model, opt, epochs=50, batch_size=128, sched=None):
    crit = nn.CrossEntropyLoss()
    losses = []
    for _ in range(epochs):
        for Xb, yb in make_dataloader_batches(batch_size):
            opt.zero_grad()
            loss = crit(model(Xb), yb)
            loss.backward()
            opt.step()
        if sched is not None:
            sched.step()
        with torch.no_grad():
            losses.append(crit(model(Xtr), ytr).item())
    return losses


model_plain = make_model('he')
losses_plain = train_mini_batch(model_plain, optim.SGD(model_plain.parameters(), lr=0.05))

model_mom = make_model('he')
losses_mom = train_mini_batch(model_mom, optim.SGD(model_mom.parameters(), lr=0.05, momentum=0.9))

print(f"plain SGD:    loss[-1] = {losses_plain[-1]:.4f}")
print(f"with momentum: loss[-1] = {losses_mom[-1]:.4f}")
    Output
    plain SGD:    loss[-1] = 0.3633
with momentum: loss[-1] = 0.0526
    Interview angle: “What does the momentum coefficient (0.9 here) actually control?”

    How much of the previous velocity carries into the current step versus how much comes from the fresh gradient: 0.9 means 90% memory, 10% new information. Push it toward 1 and the optimizer gets harder to redirect; push it toward 0 and it is closer to plain SGD.

    04

    RMSprop: a learning rate per parameter

    A new idea, not a variant of momentum.

    Momentum smooths the direction of updates. RMSprop does something different: it tracks a running average of each parameter's squared gradient and divides that parameter's step by the square root of it. A parameter with consistently large gradients gets its steps shrunk; a parameter with small, gentle gradients gets its steps amplified. Every parameter effectively gets its own learning rate.

    Code: RMSprop with torch.optim
    model_rms = make_model('he')
losses_rms = train_mini_batch(model_rms, optim.RMSprop(model_rms.parameters(), lr=0.01, alpha=0.9))

print(f"momentum: loss[-1]={losses_mom[-1]:.4f}  noise in last 20 epochs (std)={np.std(losses_mom[-20:]):.4f}")
print(f"RMSprop:  loss[-1]={losses_rms[-1]:.4f}  noise in last 20 epochs (std)={np.std(losses_rms[-20:]):.4f}")
    Output
    momentum: loss[-1]=0.0526  noise in last 20 epochs (std)=0.0482
RMSprop:  loss[-1]=0.1019  noise in last 20 epochs (std)=0.0855
    Try it: audit an AI answer

    Ask an AI to write an SGD-with-momentum config for this network. If it hands back something like lr=0.9, momentum=0.01, learning rate and momentum with their typical magnitudes swapped, don't just read the line and trust it. Run it and watch the loss curve bounce without settling. A number that “looks about right” for the wrong hyperparameter is a very easy mistake to miss by eye alone.

    Interview angle: “RMSprop reached a lower loss than momentum at first, but you must pick one to ship. Which?”

    It depends on what the loss curve is telling you. If validation performance is what matters and RMSprop's noise doesn't hurt it, ship the faster one. If stability or reproducibility across runs matters more, momentum's smoother curve may be the safer default. “Lower loss” alone isn't the full decision.

    05

    Adam: momentum and RMSprop together

    Both running averages, plus bias correction.

    Adam keeps both running averages: momentum's directional average of the gradient, and RMSprop's magnitude average of the squared gradient. There is one more piece. Both averages start at zero, so early on they are biased toward zero and understate the true gradient. Adam divides each by a correction factor that is large at step 1 and fades to 1 as training goes on. This is bias correction, and it is the reason Adam behaves sensibly in its first few steps instead of barely moving.

    How the optimizers relate

    Plain SGDone fixed step size for everything
    →
    + Momentumsmooths the direction of updates
    + RMSproprescales step size per parameter
    →
    Adamboth averages, plus bias correction for the first few steps
    →
    + LR scheduleshrinks the overall step near a minimum

    Interview angle: “Why would Adam need bias correction if momentum alone didn't need it in Class 2?”

    It isn't unique to Adam: momentum has the identical early-step bias, and Class 2 just didn't need to worry about it for a short demo. It matters more in practice with Adam because the correction interacts with the RMSprop-style denominator: an uncorrected, too-small early average in the denominator would produce an artificially huge first step.

    06

    Optimizer race on a steep, narrow valley

    The same four optimizers, now on a surface you can see.

    The surface is 0.1·x² + 2.0·y²: sharp in one direction (y), shallow in the other (x). It is a classic case where plain SGD struggles, because any learning rate large enough to make progress in the shallow direction overshoots in the steep one. All four optimizers start from the same point, (−8, 4), and take 60 steps.

    Before pressing play, predict: which path zigzags the most, and which reaches the center most directly?

    What the paths show

    Plain SGD zigzags in small, tight steps in the steep direction: its y-coordinate flips sign on nearly every step, while x advances by a fixed fraction (a factor of 0.92 per step here). One learning rate has to serve two very different slopes.

    Momentum actually swings wider, not smaller. It carries velocity from the steep initial descent straight past the flat bottom and back: a few large oscillations instead of many small ones, before settling.

    RMSprop and Adam avoid both problems. Their per-parameter scaling shrinks the step in the steep direction and grows it in the shallow one, so the path runs almost straight toward the minimum.

    Does that make momentum worse here? Not worse, different. Its swings are fewer and shrink toward the minimum instead of persisting, and how quickly they die out is governed by one number, the momentum coefficient. It is a real trade-off, not a strict upgrade, and it is exactly why RMSprop's and Adam's per-parameter scaling exists as a different fix for the same underlying problem.

    Code: the valley and the four optimizers
    def loss_fn(xy):
    x, y = xy[0], xy[1]
    return 0.1 * x**2 + 2.0 * y**2

def run_optimizer(make_opt, start=(-8.0, 4.0), steps=60):
    xy = torch.tensor(list(start), requires_grad=True)
    opt = make_opt([xy])
    path = [xy.detach().clone().tolist()]
    for _ in range(steps):
        opt.zero_grad()
        loss_fn(xy).backward()
        opt.step()
        path.append(xy.detach().clone().tolist())
    return np.array(path)

paths = {
    'SGD':      run_optimizer(lambda p: optim.SGD(p, lr=0.4)),
    'Momentum': run_optimizer(lambda p: optim.SGD(p, lr=0.1, momentum=0.9)),
    'RMSprop':  run_optimizer(lambda p: optim.RMSprop(p, lr=0.1)),
    'Adam':     run_optimizer(lambda p: optim.Adam(p, lr=0.3)),
}

xx, yy = np.meshgrid(np.linspace(-9, 2, 200), np.linspace(-5, 5, 200))
zz = 0.1 * xx**2 + 2.0 * yy**2

plt.figure(figsize=(6, 6))
plt.contour(xx, yy, zz, levels=20, cmap='Greys', alpha=0.5)
for name, path in paths.items():
    plt.plot(path[:, 0], path[:, 1], marker='.', markersize=3, label=name)
plt.scatter([0], [0], c='red', marker='*', s=150, zorder=5, label='minimum')
plt.legend(); plt.title('Same starting point, four optimizers')
plt.show()

    07

    Learning rate scheduling: why Adam still needs decay

    Adaptive scaling is relative; it doesn't shrink the overall step.

    Adam already adapts the step size per parameter, so why would it still need a schedule? Compare two runs with the same starting learning rate (0.03) over 40 epochs. In one the rate stays fixed. In the other it decays each epoch by 1 / (1 + 0.2 · epoch), and decay is the only difference.

    Why decay still helps

    Adam's per-parameter scaling adjusts the relative step sizes between parameters. It doesn't shrink the overall step as training approaches a minimum. Near a minimum, any fixed step size is eventually too big for at least some direction. Decay handles that separately.

    Code: Adam with and without decay
    model_adam_hi = make_model('he')
losses_hi = train_mini_batch(model_adam_hi, optim.Adam(model_adam_hi.parameters(), lr=0.03), epochs=40)

print("Adam, lr=0.03, no decay -- last 10 epochs:")
print([round(x, 3) for x in losses_hi[-10:]])

from torch.optim.lr_scheduler import LambdaLR

def lr_lambda(epoch, r0=0.2):
    return 1.0 / (1 + r0 * epoch)

model_adam_decay = make_model('he')
opt_decay = optim.Adam(model_adam_decay.parameters(), lr=0.03)
sched_decay = LambdaLR(opt_decay, lr_lambda=lr_lambda)
losses_decay = train_mini_batch(model_adam_decay, opt_decay, epochs=40, sched=sched_decay)

print("Adam, lr=0.03, with decay -- last 10 epochs:")
print([round(x, 3) for x in losses_decay[-10:]])

    Industry note

    Production training almost always schedules the learning rate; a constant learning rate at scale is close to a beginner's mistake. The specific schedule (this simple decay, cosine annealing, warmup-then-decay) matters less than having one at all.

    08

    Recap and rapid-fire

    What to carry forward.

    Key takeaways

    1. Identical initialization breaks a network permanently, not slowly. Symmetry never breaks on its own.
    2. Initialization scale alone can vanish or explode activations, independent of the activation function.
    3. He initialization matches ReLU's math; Xavier matches symmetric activations like tanh. Pick based on what you're using.
    4. Momentum smooths direction. RMSprop rescales step size per parameter. Adam does both, plus bias correction for its first few steps.
    5. A fixed learning rate is a ceiling on precision near a minimum, no matter how good the optimizer is. Scheduling addresses that directly.
